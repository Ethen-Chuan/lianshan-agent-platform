# 具体问题洞察、轻本体与案例关联

版本：产品演示 v0.1；编写日期：2026-11-08。

本文区分“已经做进本地 Demo 的交互”和“真实系统需要建设的能力”。涉及客户、门店、型号、问题数量、消息和日志线索的内容均为脱敏模拟样例，不代表真实经营数据。

## 一、这次要解决什么

原先的“设备故障、操作咨询、工单进度”只能回答大类分布，无法让运营人员直接派发排查工作。新的最小分析对象是有范围和证据的问题定义，例如：

- 产品：座舱终端 A1。
- 版本：V2.3.2。
- 触发环节：升级后首次通话。
- 客户现象：蓝牙连接正常但通话无声，音乐播放正常。
- 原因假设：通话音频路由可能没有恢复。
- 证据缺口：尚未排除手机系统及安装方式，缺少稳定复现。
- 下一步动作：补日志与对照复测，由终端技术组核验。

现象、原因假设、已核实原因和处理动作必须分别存储。频繁出现、语义相似或共享同一软件版本，都不足以证明因果关系。

## 三、计数必须可复算

### 1. 问题实例，而不是消息条数

生产中的建议问题实例由服务对象、服务周期和主要诉求确定。一个客户连续追问同一问题，不应把问题量放大。一个会话包含两个不同诉求，可以拆成两个实例，保留各自的消息引用。跨渠道身份未可靠关联时，不做自动合并；同时监控疑似重复比例。

演示采用固定 `SAMPLE ID` 作为问题实例，每条记录只对应一个主要问题。11 月 7 日的 514 条模拟客户消息归为 208 个问题实例；查看来源只展示代表片段，不声称已完整呈现所有消息。

### 2. 统计规则

- Top 5：当前日期、渠道、领域范围内，按不同问题实例数量降序；同量按稳定问题 ID 排序。
- 占比：该问题实例数 / 同范围全部有效问题数。Top 5 加“其他”覆盖整个分母。
- 未确认解决：明确未解决与结果待确认的总和；不把停止回复视为解决。
- 新问题量：未命中已知定义的候选实例数。候选仍留在总量分母里。
- 门店数：当前问题下的不同门店数量，不跨问题相加当全局门店数。
- 日比较：前一天；七天比较：前一周同样七天。对比期为零时展示“对比期无样本”，不展示无穷增幅。
- 空范围：无数据，不显示虚假 Top 5、满分、零风险结论或非零占比。
- 快照版本：记录数据截止、本体版本、分类器/模型版本、统计口径版本、筛选条件与生成时间。历史数据重算另存快照，不能覆盖旧结果。

## 四、轻本体如何限定已知领域（待后端建设）

先维护少量有用实体和约束，不先建设庞大的全行业知识图谱。

| 对象 | 建议关键属性 | 为什么需要 |
| --- | --- | --- |
| 产品及部件 | 产品 ID、型号、部件、别名 | 防止相似名称误关联不同设备 |
| 软件版本 | 版本、适用型号、生效时间 | 防止跨版本复用不适用方案 |
| 业务环节 | 受理、排查、送检、检测、换机等 | 区分技术问题和流程问题 |
| 问题定义 | 名称、可观察现象、触发条件、纳入/排除边界 | 保持颗粒度可操作且不重复 |
| 原因假设 | 假设内容、状态、佐证、反例、验证动作、审核人 | 不把关联当因果 |
| 案例与证据 | 问题 ID、消息 ID、原文片段、来源、时间、访问范围 | 每个结论可回查 |
| 处理动作 | 前置条件、工具、审批边界、结果验证 | 防止未经授权换机、退款或承诺 |

关系至少区分“发生于”“在某版本出现”“与某现象相似”“有证据支持某假设”“有证据反驳某假设”“经审核确认原因”。不要把所有关系都写成“导致”。

没有明确领域归属或字段缺失的样本进入“待确认”，而不是强行塞入已有类别。当前可见大类之外的未知领域需要独立的待认领入口，这是生产建设项。

## 五、GraphRAG 的位置（待后端建设）

建议把聚合统计、语义聚类和关联检索拆开建设：

1. **归一与切分**：授权读取消息，按消息 ID 幂等入库；脱敏、过滤测试/垃圾、划分诉求，并保留原文引用。
2. **已知问题识别**：先做本体别名和规则匹配，再用模型提取结构化字段。缺少产品、版本或关键触发条件时降低匹配确定性，禁止无依据填充。
3. **未知候选发现**：对未命中或低置信样本做语义表示与聚类；结合型号、版本、环节约束，排除仅措辞相似的误聚类。小簇和离群点单独保留，不因不成簇而删除高风险事件。
4. **实体与案例关联**：将授权范围内的产品、版本、现象、工单、已审核知识及案例证据关联起来。
5. **GraphRAG 检索**：按当前问题实体和业务范围检索关联案例、关系与原文片段，形成支持线索、反例和缺口。跨版本、跨产品的参考案例必须醒目标注不一致条件。
6. **统计服务**：只对结构化问题实例做确定性分组、去重和计数。语言模型负责提出候选标题和摘要，不负责生成 Top 5 的计数事实。
7. **人工核验**：运营或领域负责人检查证据，再决定合并、拆分、补充材料或新增本体定义；原因确认需要独立证据。

GraphRAG 不等于聚类算法，也不是根因证明器。客户问题聚类可以采用语义向量与约束聚类；图上的社区发现用于补充关系结构。两者都要用业务标注样本评估，不能仅因图看起来有联系就认定同一问题。

公开资料核对：Microsoft GraphRAG 官方文档《Local Search》说明其将图谱结构化信息与原文内容结合，为查询提供相关实体上下文。这里的客服本体、统计口径、未知发现、人工审核和发布门禁是本方案设计，不是官方文档承诺的现成功能。核对日期：2026-11-08。

官方资料位置：`https://microsoft.github.io/graphrag/query/local_search/`。

## 六、新问题反哺与版本治理

1. 候选生成后保留原始簇、模型建议、聚类/提取版本、来源实例及得分含义；不覆盖人工意见。
2. 人工确认问题名称、业务域、定义、正例、反例、排除范围及相近定义；同义问题优先合并，避免目录膨胀。
3. 变更形成草案，记录来源快照与基线本体版本。
4. 生产验收必须覆盖人工确认的独立正反样本，并检查误合并、误拆分、已知问题回退、未知保留率与证据引用准确性。输入、模型、本体或案例变化，旧验收失效。
5. 审核通过后分阶段启用，并保留版本回退能力；不可把规则校验通过等同于业务验收通过。
6. 历史报表默认保留旧映射。需要比较新旧定义时生成新快照，并展示口径差异，防止“优化后准确率变高”只是改了分类或分母。

本地 Demo 只实现草案的四项检查：字段完整、来源有效、存在排除样例、基线版本和重名冲突。它未运行真实模型、聚类或语义回归，也没有生产灰度和自动回退执行。

待复核案例必须先经人工判断是否真是 Bad case，补齐错误类型与期望行为，之后才能纳入研发侧回归集。不能把历史客服回复或模型自评直接当金标。研发工作台负责试跑与验收；ServiceHub 负责运行、证据回查与问题登记，两侧交付与注册机制仍需独立建设。

## 七、建议的验证指标（不是当前实测）

- 运营实用性：Top 问题中可明确派发核验动作的比例、证据可回查比例、处理到验证关闭的时长。
- 分类质量：经人工标注的细粒度分类准确情况、误合并/误拆分比例、未知问题保留情况；披露样本和分母。
- 新问题质量：候选采纳比例、发现到人工确认时长、高风险离群事件漏检情况。不能以“新增类型越多越好”为目标。
- 关联检索质量：检索案例相关性、产品/版本冲突比例、来源引用正确性、反例覆盖情况。可用同一标注集对比普通检索与 GraphRAG，再判断额外复杂度是否值得。
- 运行质量：数据新鲜度、失败/超时数量、漏采消息、重复消息、权限过滤、索引延迟、调用成本和任务重试情况。
- 人工确认根因的比例必须单独统计；不得用模型置信分、聚类相似度或规则通过率替代。

具体阈值需要客户基线和标注集校准，本方案不捏造生产达标数字。

## 八、生产接入约束

- 先接一条已经获得权限的业务线，验证从消息来源到问题实例再到证据下钻的可追溯性，再扩大渠道范围。
- 访问控制应在查询和图扩展前生效；租户、门店、人员授权与删除请求要同步到原文、向量索引、图关系和缓存。
- 每条边和摘要保留来源与访问范围。发现无权限原文时不能通过图关系或社区摘要间接泄露。
- 外部模型请求遵循最小必要和用户授权；不携带 API Key、真实身份字段或无关全文。密钥由服务端托管，不进入本体包、Trace 或导出。
- 新问题审核、根因确认、本体发布、助手启用分别授权，不能由同一个“全部通过”按钮代替。
- 持续更新采用幂等入库、可重试任务、版本化索引和失败队列。接收失败、解析失败、未知类和超时均保留在各自分母中，不静默删除。
